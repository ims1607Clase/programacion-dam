Apartado 2.1

La programación estructurada

Es la idea de fondo de todo el tema: con muy pocas herramientas se puede hacer cualquier programa, y además queda más fácil de escribir, probar y mantener.

En cristiano

Piensa en piezas de Lego. Con solo tres tipos de pieza (hacer cosas en orden, decidir entre caminos y repetir) puedes construir cualquier programa. El teorema dice eso. Y la regla de oro es que un programa tiene una puerta de entrada, una de salida y ningún pasillo que dé vueltas para siempre.

Las tres estructuras

Böhm y Jacopini demostraron en 1966 que cualquier programa propio se escribe solo con:

Secuencial, selectiva (condicional) y repetitiva.

Programa propio

Cumple las tres cosas a la vez:

1. Un único inicio y un único fin.
2. Hay un camino que pasa por todas las partes.
3. No tiene bucles infinitos.

Dijkstra

Para hacer programas más potentes en menos tiempo hay que simplificar las herramientas, no complicarlas. Ayudó a salir de la "crisis del software" de finales de los 60.

La POO (tema 3 en adelante) no sustituye a esto: dentro de cada método de una clase seguirás usando secuencial, selectiva y repetitiva. Por eso este tema es la base de todo lo demás.

Test rápido

Un detalle de los apuntes: el ejemplo de la suma lee con System.console().readLine() y convierte con Integer.parseInt. Aquí usamos Scanner (el «método ganador» del apartado 10 del Tema 1), que hace lo mismo sin conversión.

Chuleta para el examen
  • Teorema (Böhm y Jacopini, 1966): secuencial + selectiva + repetitiva bastan.
  • Programa propio: un inicio, un fin, camino que recorre todo, sin bucles infinitos.
  • Dijkstra: simplificar herramientas para ser más productivos.
  • POO = programación estructurada + clases y objetos.
Apartado 2.2

Estructura secuencial

La más simple: cada instrucción se ejecuta después de la anterior, en el orden en que está escrita. Ninguna empieza hasta que la anterior termina.

En cristiano

Es una receta de cocina: paso 1, paso 2, paso 3, sin saltarte ninguno. No puedes batir los huevos antes de romperlos. En programación casi siempre es: leer datos, calcular, mostrar el resultado.

Este es el algoritmo de los apuntes, la suma de dos números. Mira cómo cambian las variables paso a paso.

Lo que suele fallar: el orden. Si calculas suma = a + b antes de leer a y b, no tienen valor todavía (en Java ni siquiera compila).

Chuleta para el examen

  • Esquema típico: leer datos, calcular, mostrar el resultado.

Apartado 2.3

Estructura selectiva (condicional)

Ejecuta uno de varios bloques según una condición. Hay tres tipos: simple, doble y múltiple.

En cristiano

Es un portero de discoteca o un semáforo: mira un dato y decide por qué camino sigues. if es "si pasa esto, haz esto". else es "si no, haz esto otro". Un else if es una fila de preguntas: la primera que se cumple gana y se acabó, ya no se miran las demás. Un switch es una máquina expendedora: pulsas un número y te da ese producto. Si no pones break, es como si además te cayeran todos los productos siguientes.

Simple y doble

if (condición) {
    acciones          // solo si la condición es verdadera
}

if (condición) {
    acciones01        // si es verdadera
} else {
    acciones02        // si es falsa
}

La condición es una expresión lógica (verdadera o falsa). Con tres if independientes para positivo, negativo y cero, Java comprueba las tres aunque la primera ya se haya cumplido. Con if-else te ahorras comprobaciones.

Operador ternario: (condición) ? valor1 : valor2. Sirve para elegir entre dos valores (por ejemplo, asignar un mensaje a una variable). No lo uses para acciones complejas.

Else if: el orden importa

Las condiciones se evalúan de arriba abajo. En cuanto una es verdadera, se ejecuta su bloque y se sale. Prueba con distintas notas y cambia el orden de las condiciones.

Regla de los apuntes: ordena de lo más restrictivo a lo más general y comprueba primero los casos de error. else if para rangos o condiciones distintas, switch para comparar una misma expresión con valores concretos.

Switch y el olvido del break

Sin break, la ejecución sigue con los case siguientes (fall-through). Elige un día y quita o pon los break. Por defecto están quitados el del 3 y el del 4, como en el ejemplo de los apuntes.

La sintaxis con flecha (case 1, 2, 3 -> ...) no necesita break y evita este problema. La expresión del switch suele ser entera o un carácter; los reales normalmente no se admiten.

  • else if equivale a anidar un if-else dentro de un else, pero se lee mejor.

Apartado 2.4

Estructura repetitiva (bucles)

Repetir un conjunto de instrucciones un número finito de veces. Todo bucle tiene dos elementos: el cuerpo (lo que se repite) y la condición de salida (lo que lo detiene). Si nunca se cumple la salida, tienes un bucle infinito.

En cristiano

Es lavar platos: "mientras haya platos sucios, lava uno". while: miras antes de empezar (si no hay platos, no lavas nada). do-while: lavas uno y después miras si quedan (como mínimo lavas uno). for: "lava exactamente 10 platos". Un contador es ir diciendo "llevo 3". Un acumulador es una hucha: vas metiendo cosas. Un conmutador es un interruptor de luz: solo tiene dos posiciones.

while (mientras)

La condición va al principio. El cuerpo puede no ejecutarse nunca.

do-while (hacer mientras)

La condición va al final. El cuerpo se ejecuta al menos una vez.

for (para)

Condición al principio y contador automático. Se usa si sabes cuántas vueltas habrá.

Ejecútalos paso a paso

Avanza con "Siguiente" y fíjate en qué línea está, cómo cambian las variables y qué se escribe. Compara el programa while con el do-while: la variable n empieza en 10 y la condición pide n < 5.

Cómo se lee un for

Un for junta en una sola línea las tres cosas que en un while escribirías separadas.

for (int i = 1; i <= 10; i++) {
    System.out.println(i);
}
1. Inicialización

int i = 1: "empiezo contando en 1". Se hace una sola vez, al principio.

2. Condición

i <= 10: "sigo mientras no pase de 10". Se mira antes de cada vuelta.

3. Incremento

i++: "al acabar cada vuelta, sumo 1". Es lo mismo que i = i + 1.

Contadores, acumuladores y conmutadores

Contador

Entero que sube o baja en cada vuelta (i++, i--). Se inicializa antes, se modifica en el cuerpo y se usa en la condición de salida.

Acumulador

Guarda resultados sucesivos: acum = acum + n. Se inicializa antes del bucle, normalmente a 0.

Conmutador

Variable de solo dos valores (normalmente boolean) que controla la salida. Si toma más de dos valores y uno de ellos termina el bucle, es un valor centinela.

Tres errores clásicos: no dar valor inicial al contador o acumulador; no modificar la variable de la condición (bucle infinito); equivocarte con < frente a <= y repetir una vuelta de más o de menos.

Chuleta para el examen
  • Bucle = cuerpo + condición de salida. Número de repeticiones finito.
  • while: condición al inicio. do-while: al final, mínimo una vez. for: sabes las repeticiones.
  • for (inicialización; condición; incremento).

  • Conmutador: 2 valores. Centinela: valor especial que termina el bucle.
  • Con reales evita == en las condiciones.
Apartado 2.5

Instrucciones de salto

Alteran el flujo normal del programa. Los apuntes avisan: están prohibidas salvo casos muy justificados, así que úsalas lo menos posible. Son tres: break, continue y return.

En cristiano

Son botones de emergencia. break es "me voy de aquí ya". continue es "este plato no, paso al siguiente". return es "se acabó mi turno, me voy a casa". Y la cláusula guardián es un portero: si no cumples los requisitos, te para en la puerta y te despide. No te deja entrar hasta el fondo para darse cuenta allí.

break

Sale inmediatamente del bloque actual (if, switch o for). Su uso habitual es dentro de un switch.

continue

Salta el resto de la iteración actual y pasa a la siguiente. Si lo necesitas, probablemente el bucle está mal planteado.

return

Termina el método. En un void se escribe sin valor (return;). Si lo llamas desde main, el programa termina.

break y continue en acción

Cláusulas guardián

Son comprobaciones al principio de un método que descartan los casos no válidos y salen enseguida con return. Comparar los dos estilos del ejemplo de la entrada según la edad:

Con ifs anidados ("código flecha")

if (edad >= 0) {
    if (edad <= 120) {
        if (edad < 12) {
            System.out.println("Precio: 5 €");
        } else {
            System.out.println("Precio: 9 €");
        }
    } else {
        System.out.println("Edad demasiado alta.");
    }
} else {
    System.out.println("La edad no puede ser negativa.");
}

Con cláusulas guardián

if (edad < 0) {
    System.out.println("La edad no puede ser negativa.");
    return;
}
if (edad > 120) {
    System.out.println("Edad demasiado alta.");
    return;
}
// A partir de aquí la edad es válida
if (edad < 12) {
    System.out.println("Precio: 5 €");
} else {
    System.out.println("Precio: 9 €");
}

Buenas prácticas: ponlas siempre al inicio del método, que cada una sea corta (una comprobación, una acción, return) y no repartas más return por mitad del algoritmo.

En un void, return 5; no compila. El código después de un return en el mismo bloque es inalcanzable y Java no lo compila.

  • continue: pasa a la siguiente iteración.
  • return: termina el método; en void sin valor.
  • Cláusula guardián: validar al principio y salir. Evita el anidamiento y separa validación de lógica.
  • Un único punto de entrada y de salida es la tradición: usa saltos solo si compensa.
Apartado 2.6

Reglas de estilo

Un programa tiene que funcionar, pero también tiene que poder leerlo una persona. Casi siempre esa persona serás tú dentro de tres meses, sin acordarte de nada.

En cristiano

Es como los apuntes de clase. Si escribes con letra clara, títulos y márgenes, los entiendes al repasar. Si lo escribes todo apelotonado, ni tú te enteras. Las reglas de estilo son ponerle "buena letra" al código. Al ordenador le da igual; a las personas no.

Las tres partes de un algoritmo

1. Cabecera

El nombre del método, los datos que recibe y el tipo de lo que devuelve. En Java es obligatoria.

2. Declaraciones

Las variables y constantes que va a usar. En Java puedes declararlas donde quieras, siempre antes de usarlas.

3. Acciones

Las instrucciones: lo que hace el algoritmo.

public static int sumarNumeros(int n, int m) {   // CABECERA
    int suma;                                    // DECLARACIONES
    if (n <= m) {                                // ACCIONES (desde aquí)
        suma = 0;
        for (int i = n; i <= m; i++) {
            suma = suma + i;
        }
    } else {
        suma = -1;
    }
    return suma;
}

Documentación: contar qué hace tu código

Interna

Los comentarios dentro del código. El ordenador los ignora. Explican cómo está hecho.

// una línea
/* varias líneas */

Externa

Documentos fuera del programa: requisitos, diagramas, guía de instalación, manual de usuario. Explican qué debe hacer, cómo está organizado y cómo se usa.

Los comentarios deben ayudar, no estorbar. Comentar cada línea hace el código ilegible. Comenta solo donde haga falta una explicación.

Javadoc: comentarios que se convierten en una web

Javadoc es un formato especial de comentario que empieza por /**. Se escribe justo antes de una clase, atributo o método, y con él se genera automáticamente la documentación de la API en HTML. Dentro se usan etiquetas que empiezan por @.

Sangría

Lo que está dentro de un bloque lleva más sangría que la línea que lo abre. La llave de cierre se alinea con la línea que abre.

Llaves

Puedes abrir la llave en la misma línea o en la siguiente. Lo importante es ser consistente. En Java se usa más en la misma línea.

Una instrucción por línea

Con excepciones justificadas, como declarar varias variables juntas.

Apartado 2.7

Excepciones

Una excepción es algo inesperado que ocurre mientras el programa se ejecuta y lo interrumpe (un crash). Dividir entre cero, abrir un fichero que no existe o escribir letras donde se esperaba un número son ejemplos típicos.

En cristiano

Vas a sacar dinero del cajero y no tienes saldo. Un cajero mal hecho se bloquearía. Uno bien hecho dice "saldo insuficiente" y te deja seguir. try significa "intenta esto". catch significa "si falla de esta manera, haz esto otro". finally es "pase lo que pase, haz esto al final", como recoger la tarjeta.

try, catch y finally

try {
    // código que puede fallar
} catch (ArithmeticException e) {
    // qué hacer si falla por una operación aritmética
} catch (InputMismatchException e) {
    // qué hacer si el dato escrito no era del tipo esperado
} finally {
    // opcional: se ejecuta SIEMPRE, haya error o no
}
// el programa continúa aquí con normalidad
  • No puedes poner dos catch para el mismo tipo de excepción.
  • Ordénalos de lo más específico a lo más genérico: ArithmeticException antes que Exception.
  • La entrada de datos es lo que más falla: el usuario puede escribir cualquier cosa. Por eso nextInt() se encierra en un try-catch.
  • printStackTrace() ayuda a depurar, pero hay que quitarlo en la versión final para no asustar al usuario.

Pruébalo tú: dividir dos números

Escribe dos valores y mira qué líneas se ejecutan (las que se iluminan). Prueba con 10 y 2, con 10 y 0, y con hola.

Crear tus propias excepciones

Hay dos formas. La primera, lanzar con throw una excepción que ya existe pero con tu propio mensaje:

if (edad < 0) {
    throw new IllegalArgumentException("La edad no puede ser negativa");
}

La segunda, crear una clase nueva. Debe extender de Exception, su nombre acaba en Exception y su constructor pasa el mensaje a la clase padre con super. El método que la lanza lo avisa con throws en la cabecera:

public class MenorEdadException extends Exception {
    public MenorEdadException(String mensaje) {
        super(mensaje);
    }
}

public static void registrar(int edad) throws MenorEdadException {
    if (edad < 18) {
        throw new MenorEdadException("Debes ser mayor de edad");
    }
    System.out.println("Registrado");
}

Mal uso: no uses excepciones para situaciones normales (por ejemplo, salir de un bucle de lectura cuando el usuario escribe una letra). Es un error de diseño, es lento y se entiende peor que un while bien hecho. Resérvalas para errores de verdad excepcionales.

  • Propia: extends Exception, nombre acaba en Exception, super(mensaje).
  • RuntimeException = no comprobada. Exception = comprobada.
  • No usar excepciones para situaciones normales.
Apartado 2.8

Pruebas

Escribir el programa es solo el primer paso. Hay que comprobar que no falla al ejecutarse, que hace lo que debe y que es eficiente. La frase de los apuntes lo resume: nunca confíes en que tu código funciona como crees.

En cristiano

Antes de vender un coche lo pruebas: frenos, luces, arrancar en frío, subir una cuesta. No esperas a que el cliente se quede tirado. Probar un programa es intentar romperlo tú antes de que lo haga otro. Y lo que no encuentras no significa que no exista: las pruebas no demuestran que no hay errores, solo que no los has encontrado.

Verificación y validación

Verificación

¿Estamos construyendo bien el producto? Comprueba que no hay errores de ejecución.

Validación

¿Estamos construyendo el producto correcto? Comprueba que cumple lo que pidió el cliente.

Tipos de pruebas según el momento

PruebaQué prueba
UnitariaUn componente aislado (método o clase), cuando lo terminas. Es la que más se usa en esta unidad.
De integraciónVarios componentes juntos.
De sistemaEl programa completo, al final del desarrollo.
De cargaCómo se comporta con un volumen de datos real. Con 20 registros va bien; con 200 000 puede fallar o ir muy lento.
De aceptaciónEl cliente da su visto bueno, al final de todo.

Caja negra y caja blanca

Caja negra

No miras el código: pruebas qué entra y qué sale. Como no puedes probar todos los valores, los agrupas en clases de equivalencia (datos que el programa trata igual) y pruebas un valor de cada grupo.

Caja blanca

Miras el código y haces que cada camino se ejecute al menos una vez: condiciones verdaderas y falsas, bucles con 0, 1 y varias vueltas, y las llamadas a otros bloques.

Ejemplo de los apuntes: un método calcularEdad(día, mes, año). Cada parámetro tiene una clase válida y clases no válidas. Prueba a clasificar valores:

  • Además de un valor de cada clase, prueba los valores límite (los bordes), los errores típicos de usuario (un año de dos cifras) y los valores imposibles (texto donde se espera un número).
  • Las clases no lo detectan todo: el 30 de febrero pasa los rangos, pero no existe.

Recomendaciones

  • Que pruebe alguien que no ha programado el código. Quien lo escribe prueba sin querer solo lo que sabe que funciona.
  • Escribe los casos de prueba y el resultado esperado antes de ejecutarlos.
  • Si aparece un error, probablemente haya más cerca. Revisa esa zona.
  • Si las pruebas no encuentran nada, desconfía de las pruebas.

Aserciones: assert

Una aserción afirma algo que siempre debe ser cierto en un punto del programa. Si es falso, el programa se detiene: hay un error de lógica.

assert condicion;
assert condicion : "mensaje de error";   // recomendada
  • Hay que activarlas con el argumento de la máquina virtual -ea. Sin él, Java ni las evalúa.
  • Sirven para programación defensiva: comprobar invariantes (lo que nunca debe cambiar) y postcondiciones (que el resultado es correcto antes de devolverlo).
  • Úsalas en pruebas unitarias (lógica de tu propio código). No las uses para validar datos del usuario ni para fallos de integración (base de datos, red): ahí van condicionales y excepciones, porque en producción -ea está desactivado.

Mira por qué: un programador calcula mal un descuento y suma en lugar de restar.

Apartado 2.9

Depuración de programas

Las pruebas te dicen que hay un error. Depurar es averiguar dónde está y por qué pasa.

En cristiano

Eres un detective. El programa es una película y el depurador es el mando a distancia: puedes pausar, avanzar fotograma a fotograma y mirar el valor de cada variable. Así ves el momento exacto en que algo se tuerce, en vez de adivinarlo.

Los tres tipos de errores

De compilación

Los detecta el compilador y el IDE los subraya. Ejemplo: falta un ; o usas una variable sin declarar.

De ejecución

El programa arranca y la JVM lanza una excepción. Ejemplo: dividir un entero entre cero, o un InputMismatchException (cuando el usuario escribe letras donde se pedía un número).

Lógicos

Funciona, no da error, pero el resultado es incorrecto. Ejemplo: un bucle que da una vuelta de menos. Nadie los detecta solo: son los más traicioneros.

Poner System.out.println() por todas partes sirve, pero obliga a añadir y quitar código. La herramienta adecuada es el depurador del IDE.

Qué puedes hacer con el depurador

  • Punto de ruptura (breakpoint): una línea donde el programa se detiene antes de ejecutarla. Solo funciona en modo depuración. Ponlo un poco antes de la zona sospechosa.
  • Avanzar paso a paso y ver las variables y cómo cambian.
  • Pila de llamadas (Call Stack): la cadena de métodos que llevó hasta la línea actual. Es la misma información que la traza de una excepción.
  • Punto de ruptura condicional: solo detiene el programa si se cumple una condición, por ejemplo b == 0. Útil si el error sale en una vuelta muy avanzada de un bucle.

Ejemplo: un error lógico escondido

Este programa debería calcular la media de los números del 1 al 10 (5,5), pero muestra 5.0. No hay errores de compilación ni excepciones. Hazte el depurador: avanza paso a paso y mira las variables. Hay dos errores, y el segundo se esconde detrás del primero. Empieza con el primer programa y ve probando los otros.

Qué has visto. Error 1: con i < 10 el bucle no llega al 10, así que la condición debe ser i <= 10. Error 2: suma / contador son dos int, así que es una división entera y se pierden los decimales (55 / 10 da 5). Se arregla convirtiendo un operando: (double) suma / contador. El segundo error quedaba oculto porque con el bucle mal, la media daba justo 5, y parecía razonable. Por eso hay que mirar cada variable, no solo el resultado final.

Cómo depurar bien

  1. Reproduce el error y averigua con qué datos de entrada ocurre.
  2. Piensa una hipótesis y usa el depurador para confirmarla o descartarla.
  3. Acota: pon el breakpoint cerca del error y muévelo hasta encontrar la primera línea donde una variable toma un valor incorrecto.
  4. Corrige un error cada vez y vuelve a probar.
  5. Añade una prueba o una aserción que lo detecte si reaparece.

Apartado 2.10

Ejemplo integrador

Un programa completo que usa todo lo del tema: un juego de adivinar un número.

En cristiano

Hasta ahora has practicado cada técnica por separado, como aprender a freír, hervir y cortar. Aquí cocinas un plato entero usando todas. Si entiendes por qué cada estructura está donde está, ya dominas el tema.

El enunciado

  • El programa elige un número aleatorio entre 1 y 100.
  • El usuario tiene 7 intentos.
  • Tras cada intento, el programa dice si el secreto es mayor o menor.
  • Si la entrada no es un número, se avisa y no se descuenta el intento.
  • Al terminar, pregunta si quieres otra partida.

Qué estructura va en cada sitio

Parte del problemaEstructura
Elegir el número y mostrar mensajesSecuencial
Repetir partidas (al menos una)Bucle do-while
Pedir intentos mientras queden y no se haya acertadoBucle while con contador y conmutador
Decir mayor, menor o aciertoCondicional múltiple (if-else if-else)
Controlar entradas que no son númerostry-catch

No hace falta ningún break: el bucle de intentos termina solo por su condición, gracias al conmutador acertado. Los apuntes lo recomiendan como buena práctica.

Ejecútalo paso a paso

Aquí el número secreto está fijado en 42 para que puedas seguirlo (en el programa real es aleatorio). Elige un escenario y avanza. Fíjate en cuándo sube intentos y cuándo no.

Ver el programa completo 
import java.util.InputMismatchException;
import java.util.Scanner;

/**
 * Juego de adivinar un número entre 1 y 100 en un número limitado de intentos.
 *
 * @author Alumnado de 1º DAM
 * @version 1.0
 */
public class AdivinaNumero {

    public static void main(String[] args) {
        // Declaraciones
        final int MAX_INTENTOS = 7;
        Scanner teclado = new Scanner(System.in);
        String respuesta;

        // Acciones
        do {                                            // Una partida por vuelta
            int secreto = (int) (Math.random() * 100) + 1;
            int intentos = 0;                           // Contador
            boolean acertado = false;                   // Conmutador

            System.out.println("He pensado un número entre 1 y 100. Tienes " + MAX_INTENTOS + " intentos.");

            while (!acertado && intentos < MAX_INTENTOS) {
                System.out.print("Intento " + (intentos + 1) + ": ");
                try {
                    int numero = teclado.nextInt();
                    intentos++;                         // Solo cuenta si es un número

                    if (numero < secreto) {
                        System.out.println("El número secreto es MAYOR.");
                    } else if (numero > secreto) {
                        System.out.println("El número secreto es MENOR.");
                    } else {
                        acertado = true;
                    }
                } catch (InputMismatchException e) {
                    System.out.println("Eso no es un número entero. Prueba otra vez.");
                    teclado.nextLine();                 // Limpia lo que escribió
                }
            }

            if (acertado) {
                System.out.println("¡Enhorabuena! Lo has adivinado en " + intentos + " intentos.");
            } else {
                System.out.println("Se acabaron los intentos. El número era " + secreto + ".");
            }

            System.out.print("¿Otra partida? (s/n): ");
            teclado.nextLine();                         // Limpia el salto de línea pendiente
            respuesta = teclado.nextLine();
        } while (respuesta.equalsIgnoreCase("s"));

        System.out.println("¡Hasta la próxima!");
        teclado.close();
    }
}

Qué decisiones tiene el código (y por qué)

  • Estilo (2.6): cabecera, bloques de declaraciones y acciones, Javadoc, comentarios solo donde aportan, constante en mayúsculas (MAX_INTENTOS) en vez de un "número mágico", y sangría que refleja la anidación.
  • Lectura: usa nextInt() dentro del try. Si el usuario escribe letras, salta InputMismatchException. Ojo: el texto inválido se queda en el búfer, así que en el catch hay que limpiarlo con teclado.nextLine() o el error se repetiría sin dejar escribir otra vez. (Por la misma razón, tras el último nextInt() hay un nextLine() antes de leer la respuesta s/n.)
